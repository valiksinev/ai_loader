# Спецификация: сервис сопоставления номенклатуры поставщиков (демо)

Версия 0.1 · 30.09.2026 · Автор: Valik

Этот документ — единый источник требований для разработки. Всё, что здесь не описано, решается по принципу «проще и надёжнее», а спорное выносится в раздел «Открытые вопросы».

---

## 1. Контекст и цель

**Проблема.** Оптовые и торговые компании, работающие в 1С:Комплексная автоматизация 2 (КА 2), регулярно получают прайс-листы и накладные от поставщиков. Названия товаров у поставщика не совпадают с названиями в справочнике «Номенклатура» клиента («Кабель ВВГнг-LS 3х2,5 ГОСТ» против «ВВГ нг LS 3*2.5»). Сопоставлять строки приходится вручную: это часы работы в неделю, дубли карточек и ошибки в остатках и ценах.

**Целевой клиент.** Компании с большим числом поставщиков (от 10), частыми изменениями ассортимента и товарами **без единых штрихкодов и GTIN**: кабель и электротехника, стройматериалы, крепёж, металлопрокат, сантехника. Там, где есть штрихкоды и GTIN, задачу уже решает сервис 1С:Номенклатура и 1С-ЭДО. Это не наша ниша.

**Цель демо.** Проверить гипотезу на реальных данных 3–5 клиентов:
- какая точность и какой охват у автоматического сопоставления;
- готовы ли клиенты пользоваться сервисом и платить за него.

**Нагрузка демо:** до 5 клиентов, примерно по 1 файлу в день, в файле до ~5 000 строк, в справочнике клиента до ~100 000 позиций.

**Модель доступа:** на этапе демо бесплатно. Биллинг не реализуется, но модель данных должна позволять добавить его позже.

## 2. Рамки

### Входит в демо
- Веб-сервис с регистрацией и входом по email и паролю.
- Загрузка справочника номенклатуры клиента (Excel/CSV).
- Ведение списка поставщиков.
- Загрузка файла поставщика (Excel/CSV) с разметкой колонок, которая запоминается для каждого поставщика.
- Алгоритм сопоставления **без внешней языковой модели** (раздел 5).
- Экран проверки результатов человеком.
- Память подтверждённых сопоставлений (по поставщику).
- Выгрузка результата в Excel для загрузки в 1С:КА 2.
- Скрипт оценки качества на размеченных данных.
- Развёртывание на собственном сервере (Debian 12) через Docker Compose с HTTPS.

### Не входит в демо (явно)
- Прямая интеграция с 1С (обмен, HTTP-сервисы, расширения конфигурации). Только файлы на входе и выходе.
- Внешняя языковая модель. Предусматривается только интерфейс для её подключения (раздел 5.7), реализация по умолчанию — «ничего не делать».
- Биллинг и тарифы.
- Распознавание PDF, сканов и фотографий. Только табличные файлы.
- XML-файлы УПД из ЭДО. Возможно, следующий этап.
- Мобильная версия интерфейса (достаточно, чтобы работало на ноутбуке).

## 3. Термины

| Термин | Значение |
|---|---|
| Организация (тенант) | Компания-клиент сервиса. Все данные изолированы по организации |
| Справочник | Номенклатура клиента, выгруженная из 1С:КА 2 |
| Позиция справочника | Одна строка справочника (товар клиента) с кодом 1С |
| Поставщик | Контрагент клиента, от которого приходят файлы |
| Входящий файл | Прайс-лист или накладная поставщика |
| Строка поставщика | Одна строка входящего файла |
| Профиль разметки | Сохранённое соответствие колонок входящего файла полям (для каждого поставщика) |
| Память пар | Подтверждённые человеком соответствия «строка поставщика → позиция справочника» |
| Корзина | Результат сопоставления строки: `auto`, `review`, `new` |

## 4. Пользовательские сценарии

### 4.1. Регистрация и вход
- Регистрация по email и паролю. При регистрации создаётся организация, пользователь становится её владельцем.
- В демо одна организация — один пользователь. Модель данных должна допускать нескольких пользователей в организации.
- Подтверждение email не обязательно в демо.

### 4.2. Загрузка справочника
1. Пользователь загружает Excel (`.xlsx`, `.xls`) или CSV.
2. Сервис показывает первые 20 строк и предлагает указать колонки (автоматически угадывает по заголовкам, пользователь подтверждает):

| Поле | Обязательно | Комментарий |
|---|---|---|
| Код 1С | **да** | Без него результат нельзя загрузить обратно |
| Наименование | **да** | |
| Артикул | нет | Даёт точные совпадения |
| Единица измерения | нет | |
| Штрихкод | нет | |
| Бренд / производитель | нет | |
| Группа номенклатуры | нет | Помогает сузить поиск |

3. Повторная загрузка **обновляет** справочник: позиции сопоставляются по коду 1С; новые добавляются; изменённые обновляются; отсутствующие помечаются как неактивные (не удаляются, чтобы не ломать память пар).
4. После загрузки показывается сводка: сколько добавлено, обновлено, деактивировано, сколько строк с ошибками (и какие именно).

### 4.3. Поставщики
- Список поставщиков: название, ИНН (необязательно), дата последнего файла, размер памяти пар.
- Поставщика можно создать вручную или при загрузке файла.

### 4.4. Загрузка файла поставщика
1. Пользователь выбирает поставщика и загружает файл.
2. **Разметка колонок.** Если для поставщика есть профиль разметки и структура файла совпадает, он применяется автоматически. Иначе пользователь указывает:
   - номер строки заголовка (в реальных прайсах шапка часто на 5–10 строке);
   - лист (если листов несколько);
   - колонки: наименование (обязательно), артикул, единица измерения, цена, количество.
   - Профиль сохраняется для поставщика.
3. Строки без наименования, строки-заголовки групп («КАБЕЛЬ СИЛОВОЙ») и итоговые строки отбрасываются. Эвристика: нет цены и нет артикула, текст целиком заглавными буквами — вероятный заголовок группы. Отброшенные строки видны пользователю отдельным списком.
4. Запускается сопоставление (фоновая задача, раздел 7.5). Пользователь видит прогресс.

### 4.5. Экран проверки — ключевой экран продукта
Три вкладки по корзинам со счётчиками:

- **Автоматически (`auto`)** — список для выборочной проверки; любую строку можно отклонить.
- **На проверку (`review`)** — основная работа. Для каждой строки:
  - исходная строка поставщика;
  - до 5 кандидатов с оценкой, **подсветкой совпадающих и отличающихся характеристик** (например, сечение 2,5 против 1,5 — красным);
  - действия: «выбрать кандидата», «найти другой» (поиск по справочнику), «новый товар», «пропустить».
- **Новые (`new`)** — строки, для которых в справочнике нет подходящей позиции.

Требования к удобству (от них зависит экономика клиента):
- горячие клавиши: `1`–`5` — выбрать кандидата, `N` — новый товар, `S` — пропустить, стрелки — навигация;
- после действия фокус сразу переходит к следующей строке;
- массовое подтверждение: «принять все в `auto`»;
- цель: **в среднем не больше 3 секунд на одну строку `review`**.

Каждое решение человека записывается в память пар (раздел 5.6) и в журнал решений (для оценки качества).

### 4.6. Выгрузка
- **Файл сопоставления** (`.xlsx`) для загрузки в 1С:КА 2: строка поставщика → код 1С, плюс цена и единица измерения, если есть. Точный набор и порядок колонок — см. открытый вопрос О-1. Формат выгрузки реализуется как отдельный настраиваемый шаблон, чтобы его можно было поменять без изменений в логике.
- **Файл новых товаров** (`.xlsx`): строки корзины `new` с извлечёнными характеристиками — заготовка для заведения карточек.
- **Отчёт по файлу:** сколько строк в каждой корзине, сколько подтверждено, отклонено и исправлено.

## 5. Алгоритм сопоставления

Главный принцип: **ошибка хуже медлительности**. Строка, неправильно отнесённая в `auto`, ломает остатки и цены клиента и подрывает доверие ко всему сервису. Лучше отправить строку на проверку, чем ошибиться.

Алгоритм — конвейер из независимых шагов. Каждый шаг тестируется отдельно.

### 5.1. Нормализация (и для справочника, и для строк поставщика)
- нижний регистр, `ё` → `е`;
- латиница, похожая на кириллицу, в русских словах и наоборот (`BBГ` → `ввг`) — по словарю похожих символов;
- единый разделитель размеров: `3*2.5`, `3x2,5`, `3х2.5`, `3 х 2,5` → `3х2,5`;
- десятичный разделитель — запятая;
- единицы измерения: `мм2`, `мм²`, `кв.мм` → `мм2`; `м`, `м.`, `метр` → `м`; `шт`, `шт.` → `шт`;
- словарь сокращений (конфигурируемый файл): `бух.` → `бухта`, `оц.` → `оцинкованный` и т. п.;
- удаление шума: лишние пробелы, кавычки, повторяющаяся пунктуация.

Нормализация — отдельный модуль с набором правил в конфигурации (TOML), а не в коде: правила будут часто дополняться. Конфигурация перечитывается без пересборки бинарника.

### 5.2. Извлечение характеристик
Из нормализованного наименования извлекается структура, например:

```json
{"тип": "кабель", "марка": "ввгнг-ls", "жилы": 3, "сечение": 2.5, "длина": null, "бренд": null, "гост": true}
```

- Реализация: регулярные выражения и словари, организованные в **отраслевые профили** (плагины). Для демо — два профиля: **кабельно-проводниковая продукция** и **крепёж** (диаметр, длина, класс прочности, покрытие, стандарт DIN/ГОСТ). Плюс общий профиль: бренд по словарю, числа с единицами.
- Профиль для организации выбирается в настройках (можно несколько).
- Характеристики справочника извлекаются один раз при загрузке и хранятся.

### 5.3. Точные совпадения (без оценки, сразу в `auto`)
По порядку:
1. Память пар для этого поставщика (раздел 5.6) — по нормализованному наименованию и артикулу поставщика.
2. Штрихкод, если он есть с обеих сторон.
3. Артикул поставщика = артикул позиции справочника — **только** если совпадение единственное и у позиции тот же бренд (или бренд неизвестен).

### 5.4. Подбор кандидатов
Для остальных строк — топ-20 кандидатов из активных позиций справочника:
- TF-IDF по символьным n-граммам (3–5) нормализованных наименований с косинусной близостью. Реализуется в крейте `matcher-core` самостоятельно: разреженные векторы + инвертированный индекс по n-граммам (готового аналога `scikit-learn` в Rust нет; объём кода небольшой, но нужен набор тестов, сверяющих результат с эталоном из Python-скрипта на одних данных). Индекс строится при загрузке справочника и сериализуется на диск (`serde` + `bincode`);
- дополнительно крейт `rapidfuzz` (аналоги `token_set_ratio`, `partial_ratio`) для переранжирования;
- если известна группа номенклатуры или тип из характеристик — приоритет кандидатам той же группы или типа.

Модели эмбеддингов в демо **не используются**. Интерфейс подбора кандидатов должен позволять добавить их позже без переделки конвейера.

### 5.5. Оценка и распределение по корзинам
Для каждого кандидата вычисляются признаки:
- текстовые близости (TF-IDF cosine, rapidfuzz-метрики);
- совпадение характеристик: число совпавших, число **конфликтующих** (оба значения известны и различаются), число неизвестных;
- совпадение единиц измерения;
- совпадение бренда;
- совпадение артикула (частичное или полное).

Правила:
- **Любой конфликт по ключевой числовой характеристике** (сечение, число жил, диаметр, длина, класс прочности) → кандидат не может попасть в `auto`, независимо от текстовой близости.
- Итоговая оценка — взвешенная сумма признаков. Веса и пороги задаются в конфигурации.
- `auto`: оценка лучшего кандидата ≥ `T_auto` **и** отрыв от второго кандидата ≥ `margin` **и** нет конфликтов.
- `new`: оценка лучшего кандидата < `T_new`.
- иначе `review`.
- Пороги подбираются скриптом оценки (раздел 6) так, чтобы точность в `auto` была **не ниже 98%**. Стартовые значения — консервативные: сначала лучше больше `review`.

Задел на будущее: когда накопится от ~2 000 решений человека, веса можно заменить обученным классификатором на журнале решений. Обучение — в Python (`scripts/`), применение — в Rust. Поэтому начинать с логистической регрессии: её коэффициенты экспортируются в простой файл и применяются в Rust одной формулой, без ML-библиотек. В демо — только подготовить выгрузку признаков и решений в CSV для обучения.

### 5.6. Память пар
- Ключ: (организация, поставщик, нормализованное наименование поставщика, артикул поставщика) → код позиции справочника **или** отметка «новый товар».
- Записывается при каждом решении человека. Отклонение автоматического сопоставления тоже записывается (отрицательная пара): эта пара больше никогда не предлагается автоматически.
- Если позиция справочника стала неактивной, пара помечается как требующая проверки.
- Пользователь может просматривать и удалять пары поставщика.

### 5.7. Интерфейс для языковой модели (задел, не реализуется)
- Абстракция `MatchingAdvisor` с методом, который получает строку поставщика и кандидатов и возвращает выбор (или «нет совпадения»), обоснование и извлечённые характеристики.
- Реализация по умолчанию `NoopAdvisor` ничего не меняет.
- Будущая реализация будет работать через API (ключ в переменной окружения `LLM_API_KEY`, включается флагом `LLM_ENABLED=false` по умолчанию) и вызываться **только для строк `review`**.
- Уверенность, которую называет сама модель, не использовать напрямую как вероятность. Только как один из признаков в калиброванной оценке.

## 6. Оценка качества

Это обязательная часть демо, а не «потом». Без цифр демо бесполезно.

### 6.1. Синтетические данные
Генератор (`scripts/generate_synthetic.py`) создаёт:
- справочник на ~5 000 позиций в двух отраслях (кабель, крепёж) с реалистичными названиями и **намеренными дублями**;
- 3 «поставщика» с разными стилями названий: сокращения, перестановка слов, латиница вместо кириллицы, опечатки, другие единицы, лишние слова («ГОСТ», «ТУ», «(бухта 100м)»);
- у каждого входящего файла — эталонная разметка правильных ответов, в том числе строки, которых нет в справочнике;
- файлы с «грязной» структурой: шапка на 7-й строке, объединённые ячейки, строки-заголовки групп.

Оговорка: синтетика доказывает только то, что код работает. Настоящая проверка — на данных клиентов.

### 6.2. Оценка на реальных данных
Скрипт `scripts/evaluate.py` (Python) вызывает CLI `matcher` (раздел 7.8) и считает метрики по его выводу. Логику сопоставления не дублирует.
- вход: справочник, входящий файл, эталон (файл «строка → правильный код», например выгрузка уже сделанных вручную сопоставлений из 1С клиента);
- выход:
  - **точность в `auto`** (главная метрика, цель ≥ 98%);
  - **охват `auto`** (доля строк, цель на старте ≥ 50%);
  - точность лучшего кандидата в `review` (показывает, насколько быстро человек будет проверять);
  - полнота `new` (сколько по-настоящему новых товаров попали в `new`);
  - список всех ошибок `auto` с признаками — для разбора;
  - кривая «порог → точность/охват» для подбора `T_auto`.

## 7. Архитектура и стек

### 7.1. Разделение языков
- **Rust** — всё, что входит в продукт: веб-сервис, воркер, конвейер сопоставления, CLI.
- **Python** — только офлайн-инструменты разработки, не входящие в продукт: генератор синтетических данных, оценка качества, подбор порогов, графики, в будущем — обучение классификатора. Python не устанавливается на сервер и не попадает в Docker-образ сервиса.
- **Связь между ними — только через CLI и файлы.** Python-скрипты вызывают Rust-бинарник `matcher` и читают его вывод (JSON/CSV). Никаких FFI-привязок (PyO3 и т. п.) в демо: так проще и не появляется второй вариант алгоритма.
- **Единственная реализация алгоритма — в Rust.** Python не должен дублировать логику сопоставления. Исключение: эталонный расчёт TF-IDF для тестов сверки (раздел 5.4).

### 7.2. Стек Rust
| Слой | Выбор | Почему |
|---|---|---|
| Язык | Rust (stable, edition 2021), Cargo workspace | |
| Веб | `axum` + `tokio` | Стандарт де-факто, хорошо сочетается с `tower` |
| Шаблоны | `minijinja` + HTMX, минимум JS (горячие клавиши на экране проверки — небольшой ванильный JS) | Шаблоны правятся без пересборки; без отдельного фронтенд-проекта |
| База | PostgreSQL 16 | Надёжно; `pg_trgm` для поиска «найти другой» |

### 7.3. Стек Python (только `scripts/`)
- Python 3.12, зависимости через `uv` (`pyproject.toml` в папке `scripts/`).
- `pandas`, `openpyxl` — чтение и запись таблиц; `matplotlib` — графики «порог → точность/охват»; `scikit-learn` — эталон TF-IDF для тестов сверки и будущее обучение классификатора.
- Тесты скриптов: `pytest` (минимально: генератор создаёт корректные файлы и эталон).

### 7.4. Компоненты (Docker Compose)
- `app` — веб-сервис на `axum` (интерфейс и API);
- `worker` — фоновые задачи: разбор файлов, построение индекса, сопоставление;
- `db` — PostgreSQL, данные на именованном томе;
- `caddy` — обратный прокси и HTTPS.

Загруженные файлы хранятся на томе `uploads/` с путём по организации. Исходные файлы клиента не удаляются (нужны для повторной оценки); срок хранения — настройка.

Образ собирается многоступенчато (`cargo-chef` для кэширования зависимостей), итоговый образ — `debian:bookworm-slim` с бинарниками `app` и `worker`, шаблонами и конфигурацией.

### 7.5. Фоновые задачи
Типы: `import_catalog`, `build_index`, `parse_supplier_file`, `run_matching`. У задачи есть статус, прогресс (0–100) и текст ошибки. Интерфейс опрашивает статус через HTMX раз в 2 секунды.

### 7.6. Модель данных (основные таблицы)
- `organizations` (id, name, created_at, settings JSON — отраслевые профили, пороги)
- `users` (id, organization_id, email, password_hash, role, created_at)
- `catalog_items` (id, organization_id, code_1c, name, name_norm, article, unit, barcode, brand, group_name, attributes JSON, is_active, updated_at) — уникальность (organization_id, code_1c)
- `suppliers` (id, organization_id, name, inn, created_at)
- `column_profiles` (id, supplier_id, sheet, header_row, mapping JSON, header_signature)
- `supplier_files` (id, organization_id, supplier_id, filename, storage_path, status, row_count, uploaded_by, uploaded_at)
- `supplier_rows` (id, file_id, row_number, raw JSON, name, name_norm, article, unit, price, qty, attributes JSON, is_skipped, skip_reason)
- `match_results` (id, row_id, bucket, best_item_id, score, candidates JSON — топ-5 с признаками, status: pending/accepted/rejected/new/skipped, decided_by, decided_at)
- `pair_memory` (id, organization_id, supplier_id, name_norm, article, catalog_item_id NULL, is_new, is_negative, needs_review, created_at, source_result_id)
- `decision_log` (id, result_id, action, chosen_item_id, features JSON, created_at) — для оценки и будущего обучения
- `jobs` (id, organization_id, type, payload JSON, status, progress, error, created_at, started_at, finished_at)

**Изоляция данных:** каждый запрос к данным фильтруется по `organization_id` текущего пользователя на уровне слоя доступа к данным, а не в каждом обработчике. На это нужны тесты: пользователь одной организации не может получить данные другой ни через интерфейс, ни через API.

### 7.7. Структура репозитория (ориентир)
```
Cargo.toml                 # workspace
crates/
  matcher-core/            # библиотека: весь алгоритм, без БД и сети
    src/
      normalize.rs         # нормализация
      attributes/          # отраслевые профили извлечения характеристик
      tfidf.rs             # TF-IDF по символьным n-граммам + индекс
      candidates.rs        # подбор кандидатов (TF-IDF + rapidfuzz)
      scoring.rs           # признаки, оценка, корзины
      memory.rs            # логика памяти пар (трейт хранилища)
      advisor.rs           # трейт MatchingAdvisor + NoopAdvisor
      parsing.rs           # чтение Excel/CSV, поиск шапки, заголовки групп
      export.rs            # шаблоны выгрузки
    tests/                 # тесты и снапшоты на наборах примеров
  matcher-cli/             # бинарник `matcher`: сопоставление файлов без веба
  db/                      # sqlx: модели, запросы, миграции, фильтр по organization_id
  web/                     # бинарник `app` (axum)
    templates/             # minijinja + HTMX
    static/
  worker/                  # бинарник `worker`
config/
  normalization.toml
  abbreviations.toml
  scoring.toml             # веса и пороги

scripts/                   # Python, только офлайн-инструменты

  generate_synthetic.py
  evaluate.py              # вызывает `matcher`, считает метрики, строит графики

docker-compose.yml

```

**Принцип:** `matcher-core` не знает о базе данных и вебе. Он получает данные и конфигурацию и возвращает результат. Хранилище памяти пар передаётся через трейт. Благодаря этому этап 1 целиком делается и проверяется через CLI, а веб и воркер потом используют ту же библиотеку.

### 7.8. CLI `matcher`
Нужен для этапа 1 и для скрипта оценки. Минимальный набор команд:
- `matcher index --catalog catalog.xlsx --mapping mapping.toml --out index.bin` — построить индекс справочника;
- `matcher match --index index.bin --input supplier.xlsx --mapping supplier_mapping.toml [--memory memory.json] --out result.json` — сопоставить файл; результат содержит для каждой строки корзину, топ-5 кандидатов и все признаки;
- `matcher export --result result.json --template config/export_ka2.toml --out export.xlsx` — выгрузка.

Формат `result.json` фиксируется JSON-схемой в репозитории: это контракт между Rust и Python.

## 8. Нефункциональные требования

- **Производительность:** файл в 5 000 строк против справочника в 100 000 позиций обрабатывается не дольше 2 минут на сервере с 2 vCPU и 4 ГБ памяти (уточнить реальные характеристики сервера, открытый вопрос О-3).
- **Ограничения загрузки:** файл до 20 МБ, до 50 000 строк; только `.xlsx`, `.xls`, `.csv`. Проверка по содержимому, а не только по расширению.
- **Кодировки CSV:** UTF-8 и Windows-1251 (автоопределение); разделители `;` и `,`.
- **Надёжность:** ошибка в одной строке файла не роняет обработку всего файла; такие строки попадают в список ошибок.
- **Журналирование:** структурированные логи без содержимого файлов клиентов.
- **Резервные копии:** ежедневный `pg_dump` и архив тома `uploads/`, хранение 14 дней. Скрипт и инструкция по восстановлению.

## 9. Безопасность

- **Секреты** (пароль БД, секрет сессий, будущий `LLM_API_KEY`) — только в `.env` на сервере. `.env` в `.gitignore`, в репозитории только `.env.example` с пустыми значениями. Никогда не коммитить секреты и не выводить их в логи.
- Пароли пользователей — только хеш `argon2`.
- Сессии — cookie с флагами `HttpOnly`, `Secure`, `SameSite=Lax`; защита от CSRF для форм.
- Ограничение частоты попыток входа.
- **Сервер (Debian 12)** — выполнить до развёртывания:
  - создать пользователя с `sudo`, вход только по SSH-ключу;
  - в `sshd_config`: `PermitRootLogin no`, `PasswordAuthentication no`;
  - файрвол (`ufw` или `nftables`): открыты только 22, 80, 443;
  - `unattended-upgrades` для обновлений безопасности;
  - PostgreSQL не публикуется наружу (только внутренняя сеть Docker).

## 10. Развёртывание

- Сервер: Debian 12, Финляндия. Домен для демо — технический домен хостера (`vds2911529.my-ihor.ru`); для продукта позже — собственный домен. Домен задаётся переменной `APP_DOMAIN` в `.env`, в коде не прописывается.
- Установка: Docker Engine + Compose plugin из официального репозитория Docker.
- `docker compose up -d` поднимает все сервисы; миграции `sqlx migrate` применяются при старте `app`.
- Caddy автоматически получает сертификат для `APP_DOMAIN`.
- В `README.md` — пошаговая инструкция: подготовка сервера, первый запуск, обновление, резервное копирование и восстановление.
- Скрипт `scripts/deploy.sh`: `git pull` → `docker compose build` → `docker compose up -d` → проверка `/health`.

## 12. Открытые вопросы

- **О-1. Формат загрузки в 1С:КА 2.** Точный набор колонок для загрузки номенклатуры поставщиков и цен поставщика в КА 2 (зависит от релиза). Проверить на реальной базе КА 2 до этапа 4. До этого — шаблон `export_ka2.toml` с предположительными колонками: наименование поставщика, артикул поставщика, единица измерения, код номенклатуры 1С, цена.
- **О-2. Отраслевые профили.** Кабель и крепёж выбраны для демо как примеры. Окончательный выбор зависит от первых клиентов.
- **О-3. Характеристики сервера.** Нужны CPU, память, диск (`nproc; free -h; df -h /`) для проверки требований раздела 8.
- **О-4. Хранение исходных файлов.** Сколько хранить загруженные файлы клиентов (предложение: 90 дней).
- **О-5. Языковая модель.** Подключать ли её и какую — решается по результатам этапа 1 на реальных данных: если без неё точность и охват достаточны, не подключать.
